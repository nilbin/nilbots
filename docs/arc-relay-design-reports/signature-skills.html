#Verdict

The sixteen signatures are a good source of tactical depth, but the current Tactics surface does not yet let a player use that depth reliably. The main problem is not a shortage of skills. It is that automatic uses are broad, authored uses are too weakly constrained, and ordinary Fight leaves are materialized before signature leaves. A skill can therefore be invisible in the editor, fire for the wrong reason, or be starved by the combat behavior it was meant to shape.

Promote one small, consistent player model:

  • every bot has one phase-local skill policy: Smart, Prefer marks, Only at marks, or Off;
  • marks are drawn on the same map as posts and routes and are stored by bot slot, not by class;
  • the authoring catalog declares each skill's mark shapes, target choices, safe smart predicate, commitment behavior, and place in the ordinary Instruction list;
  • the Tactic compiler still emits only ordinary, top-to-bottom Instructions; there is no skill scheduler, reservation system, or second priority model;
  • an illegal or unavailable use falls through in the same tick;
  • active tells/channels that must be preserved get one ordinary signature-commitment-active -> current-position continuation above normal actions.

The moving frontal shield is a strong fit for Palisade and is now promoted as Prism Screen in Tapline-12. It does not replace Mason's Hardlight Block: keeping a mobile screen and a static route-bending block creates two distinct strategic jobs. The first tuning point is 30 shield hull, 6 active ticks and 18 cooldown ticks. These values are acceptance-proven mechanics, not a claim that population balance is already settled.

#Why the current authoring is not yet reliable

#1. Fight currently wins before the skill can shape the fight

ArcRelayTacticsMaterializer.cs:780-818 emits custody, recovery, destination Fight and travel Fight before signatures. Most unmarked signatures are gated on enemy-nearby, the same situation that makes Fight eligible. The earlier Fight leaf wins. Palisade, Towline, Hush, Sunder, Repulsor and other combat signatures can therefore be silently starved.

This is not solved by putting every skill above every action with a broad condition. Smart predicates must first become conservative enough that a higher skill leaf means “this is a useful opportunity,” not merely “cooldown is ready.”

#2. Commitment is described but not compiled

The authoring catalog marks Kestrel, Towline, Patchbay, Mortar, Hush, Switchback, Longshot, Sunder, Repulsor and Nest as PreserveByDefault. The Tactics materializer never consumes that metadata. The lower Orders vocabulary already supports signature-commitment-active, and focused Orders scenes prove an intentional hold for Repair and Rail, but Tactics does not generate it.

Result: a new phase action or floor move can cancel a rooted tell/channel. Add one body-local continuation derived from the authoritative operation state; do not copy tell/duration numbers into the Tactic.

#3. Marks are keyed by class, not by bot

ArcRelayTacticsDsl.cs:955-1026 validates one mark set per class, and the web stores job.sigs[bot.class] (MapFirstChrome.tsx:448-514). The roster rules permit one duplicate wildcard. Two Masons, Relays, Palisades, or any duplicated class cannot receive independent skill policies or geometry.

The source must be keyed by stable squad slot. A deterministic migration can copy a legacy class mark to every matching slot in that group and mark the result for review; new documents must never collapse it back by class.

#4. A spatial mark is currently only a target, not an opportunity

Exact points compile with signature-ready and a default named target. They do not express occupancy, friendly-fire safety, meaningful effect, current deployment state, or whether the caster is at the intended firing post. Longshot is the clearest correctness bug: its Rail use precedes and is not conditioned on its drawn stand position (ArcRelayTacticsMaterializer.cs: 1405-1435).

#5. Several public descriptions do not match runtime truth

  • Survey Flare is anti-smoke, not independent reveal.
  • Kinetic Burst currently pushes and does no damage.
  • Sentinel can select enemies without team-visible contact.
  • Falling Star ignores allied bodies, matching the rest of the signature band.
  • Exchange drops the targeted ally's Core but lets the casting Switchback transport its own Core through the swap.
  • Falling Star's catalog timing says completion-anchored cooldown while its behavior sets cooldown at activation.

These may be valid rules, but they must be deliberate, tested and explained before the editor automates them.

#One map-first skill authoring model

#Player surface

Selecting one bot in one phase should open its existing bot drawer and show:

  1. signature name and a one-sentence rule summary;
  2. one segmented policy control:
    • Smart — use the catalog's conservative default inside this phase;
    • Prefer marks — try authored opportunities first, then Smart;
    • Only at marks — never use outside authored opportunities;
    • Off — do not author a use leaf in this phase;
  3. the relevant draw tool: point, zone, route segment, firing post + aim, facing handle, or protected/target bot;
  4. a plain-language preview such as “Wall while crossing this segment, facing forward” or “Mortar this area only when no ally is in the cross”;
  5. an optional advanced toggle: Must happen before this phase can finish.

Must happen is not a reservation or atomic cast. It adds phase-local evidence from an accepted/completed signature operation to the existing phase exit condition. The UI must require a maximum phase duration or warn about a possible deadlock. Normal “Only at marks” merely constrains opportunities and does not hold the phase open.

#Suggested source shape

The exact names can follow repository conventions, but the semantic ownership should be explicit and slot-local:

{
  "skillPlans": {
    "2": {
      "mode": "prefer",
      "requiredBeforeExit": false,
      "opportunities": [
        {
          "kind": "route-segment",
          "line": [[8, 14], [18, 14]],
          "facing": "route-forward"
        }
      ]
    }
  }
}

The catalog—not UI switches—declares which opportunity kinds and target options are legal for each signature. Extend the existing ArcRelaySignatureAuthoringDescriptor with data such as:

  • OpportunityKinds: point, zone, route segment, post-and-aim, friendly target;
  • DefaultPolicy and safe smart preset;
  • InstructionBand: custody, commitment, opportunity, or transit;
  • PreserveCommitment;
  • deployment ownership/replacement warning;
  • preview footprint/range semantics from the resolved Engine definition.

Numeric timing, range, damage and duration continue to come from the resolved Engine rules projected by the App. Do not duplicate balance constants in web code or TacticalPlaybooks.

#Ordinary Instruction order

Keep the Tactic phase coordinator as the only state machine. For each body in the selected phase, materialize a visible ordinary order band:

  1. active Tactic-wide abort/phase decision (existing coordinator);
  2. preserve an already-active signature commitment where the descriptor says it must be preserved;
  3. Core custody branch, including Relay Toss where applicable;
  4. urgent recovery;
  5. useful marked/Smart signature opportunity;
  6. ordinary Fight;
  7. scan;
  8. authored route/post/patrol movement and fallback.

Kestrel's route Dash lives in the transit portion of step 5 and remains empty-handed. Relay Toss lives inside custody, not as a parallel generic skill system. All other signatures use the same opportunity slot. If the selected use cannot be admitted, it falls through to Fight or movement that tick.

This ordering is deterministic and inspectable. The generated explanation can say exactly which higher leaf won. There is no cooldown scheduler, no “skill AI” ticking beside Instructions, and no hidden priority between a Tactic and a skill.

#Palisade moving frontal shield implementation

#Clarify the class ownership

Palisade historically owned Prism Wall. Mason owns Hardlight Block. The promoted moving shield is a new Prism Wall envelope for Palisade—display name Prism Screen—not a Mason rewrite.

That leaves a useful class pair:

  • Palisade: mobile, directional projectile protection for a convoy or corridor advance;
  • Mason: static, killable terrain that redirects bodies and shots.

Giving Mason the moving screen or deleting Hardlight would collapse two different map decisions into one.

#Smart and authored behavior

Smart use is conservative:

  • Palisade is moving/holding inside the current Tactic's geometry;
  • a hostile projectile lane, pending Rail line, or visible ranged threat is in the front half-plane;
  • the screen protects Palisade, a carrier, or another ally behind it;
  • no healthy active screen already covers that lane.

Player controls:

  • on a post: face a map anchor and screen when the lane is threatened;
  • on a route/patrol: mark eligible segments and select face route forward or a fixed facing;
  • Prefer marks allows reactive Smart use elsewhere in the phase;
  • Only at marks supports a deliberately timed corridor crossing.

Authored facing always wins. Smart must not rotate every tick toward the nearest enemy; that would create opaque shield dancing and erase flank counterplay.

#Counters and fun case

The shield creates readable answers rather than a universal damage reduction:

  • flank or rear fire bypasses it;
  • focus fire breaks 30 hull;
  • Rail consumes most of it but is stopped once;
  • Mortar attacks the packed formation/footprint;
  • Hush suppresses it;
  • Towline or Repulsor can disturb the screen formation;
  • Mason can alter the route in front of it;
  • smoke can cut the convoy's own target knowledge.

That interaction web is why the change is more promising than simply adding hull to Palisade.

#Engine and presentation implications

Implement it as a new concrete signature definition variant under a new loop profile/rules fingerprint. Historical Prism Wall definitions and replay bytes must remain resolvable. Keeping stable action/signature id prism-wall is reasonable if the new definition is versioned like SentinelSeed2; use the display name Prism Screen in the new catalog.

Required runtime work:

  • derive operation positions from live owner position/facing after movement;
  • remove it on owner death and suppress it under hostile Null Field;
  • consume real damage rather than contact count in the new durable envelope;
  • make projectile and Rail collision use the derived positions;
  • keep it out of body collision and static pathfinding;
  • project movement/facing changes into every replay snapshot.

The current 2D/3D Prism presentation assumes static operation positions. Either parent the visual to the Palisade transform or update projected positions every frame/tick. Test turns, route corners, damage state, expiry, suppression, death and replay seek; avoid a one-tick visual lag. This is a presentation-mechanics change and should version the signature presentation package if the replay contract requires it.

#Combat behavior under Tapline-11 movement rates

Tapline-11 makes swift/standard/deliberate real 1/1, 4/5, and 2/3 movement cadences under one Combat Strafe control model. That difference can create useful combat identity, but it must be a visible posture preset rather than hidden class AI.

Suggested fight presets:

  • Hold line: defend the authored post/zone; slower/deliberate bodies screen lanes and do not auto-strafe.
  • Pressure: current bounded approach/chase behavior.
  • Mobile flank: during the existing gun reload window, a quick body may take a bounded side/rear angle inside the active Tactic geometry, then fire or return. This is recommended for Kestrel, Lantern, Relay and Veil, not silently forced on them.
  • Screen carrier: Palisade/Mason/Repulsor occupy the authored lane between a carrier and known fire, without inventing a separate escort scheduler.

Guardrails for Mobile flank:

  • authored posts, facing and routes always win;
  • maximum 2 displacement steps from the episode anchor before return;
  • every step must improve a stable flank goal or return progress;
  • target loss, phase change, Core pickup or route departure ends the episode;
  • do not choose a new “best” side every tick;
  • no back-and-forth kiting against a fixed target and no local orbit;
  • log the ordinary Fight/move reason in Practice.

The rear 2x multiplier makes a bounded reload-window flank potentially very strong. Swift classes also use the two-tick short-gun interval, normally leaving only one reposition tick before the next shot. Start with an explicit opt-in that stops when the shot is ready; any preset that deliberately gives up one ready shot for a second flank step must say so. Run orbit/reversal gates before considering it a default for swift bodies.

Signature interactions with those roles are natural: Kestrel Dashes along the bounded flank route, Veil Smokes a crossing, Lantern counters smoke, Relay uses mobility for custody rather than free combat kiting, Palisade screens the lane, Longshot/Mortar/Nest hold authored ground, and Towline/Sunder exploit the contacts the flank produces.

#Ranked implementation plan

  1. Change Tactics signature ownership from class-keyed to slot-keyed; migrate legacy marks deterministically and add duplicate-class tests.
  2. Add the four policy values and catalog-declared opportunity kinds. Keep Smart as the no-configuration default, but make risky terrain skills such as Mason eligible for Only at marks as their catalog default.
  3. Materialize catalog commitment continuation and useful signature opportunities before ordinary Fight; keep Relay inside custody and Kestrel empty-handed/route-bound.
  4. Fix Longshot's on-station gate and show firing post/aim/range/team-vision requirements.
  5. Reconcile Falling Star cooldown metadata/runtime, preserve its documented allied immunity, decide/document Exchange Core asymmetry, and decide Sentinel vision ownership.
  6. Make Survey Flare copy and Smart predicate match anti-smoke reality, or version it into a real sensor before advertising reveal.

  3. Add deployment replace warnings and “existing deployment still useful” guards for Prism/Trip/Hardlight/Sentinel.

#Unresolved owner decisions

These should be answered before calling Smart skills player-ready:

  1. Survey Flare: explicitly anti-smoke, or a real temporary sensor? The recommendation is to make its UI honest immediately, then test a sensor variant separately.
  2. Sentinel perception: require existing team contact, or give the seed an explicit projected sensor? The recommendation for alpha is team contact; an autonomous sensor is a larger vision/balance feature.
  3. Falling Star friendly fire: resolved by owner decision; allied bodies are immune, and the editor still previews the hostile cross and tell.
  4. Exchange and Cores: retain “caster transports, target drops,” or make both sides drop? The current asymmetry is strategically interesting but surprising.
  5. Palisade tuning: Tapline-12 resolves the footprint as three derived front tiles. Population play still needs to validate the initial 30/6/18 tuning and whether body-overlap deactivation is sufficiently legible.

#Final recommendation

Do not add more signature mechanics yet. Make these sixteen understandable, slot-specific and dependable through one map-first policy model, then validate the newly promoted Palisade screen in ordinary authored play. That pass should produce substantially more playable depth than another class would: players will be able to draw a route, post, lane or target relationship and trust the bot to use its unique tool for a visible reason, while the underlying game remains one ordered Instruction executor.
