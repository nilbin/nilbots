### 5. Why 120–160 cells take this long

The approximately 25-second slow cell is an **audit cell**, not 25 seconds of
live-server CPU for one match. A cell runs the match, constructs the canonical
record, regenerates and deep-verifies the replay, produces the compressed
broadcast, computes the scorecard and eligibility facts, and pays short-lived
process/JIT/module startup. Deep verification checks the replay; it does not
run a second simulation.

| Measurement | Value |
| --- | ---: |
| 160-cell WASM screen, four workers | 697.651 s wall |
| Throughput-equivalent wall time per cell | 4.36 s |
| Individual audited cell wall time, min / mean / max | 12.11 / 17.28 / 25.77 s |
| 10-cell repair screen, four workers | 49.030 s wall |
| Deferred 992-cell exhaustive projection at measured throughput | about 72 min |

A separate Release spot measurement isolated a 350-tick match at 8.61 seconds
wall / 9.65 seconds CPU with about 1.28 GB peak RSS. Deep replay verification
was another 3.87 seconds wall / 3.98 seconds CPU in its own process and peaked
around 2.46 GB RSS. Those peaks are not additive, but both the CPU path and the
allocation pressure are too high to accept as the final production host.

At the current 5 Hz simulation rate, the isolated 350-tick match represents 70
seconds of game time, so the present one-shot path is roughly 13.8% of one core
per continuously running match. That suggests about 4–5 simultaneous matches
per core with reasonable headroom, before networking and service overhead. It
is a directional capacity estimate, not a production benchmark: a real host
should keep the process warm, share compiled WASM modules, pool participant
runtimes, stream replay capture, and perform deep verification and scorecard
reduction asynchronously or by sample rather than inline.

The sparse registered counter-web was therefore the correct audit economy: it
cut this stage from a projected 992 cells to 160 without pretending to be the
exhaustive product-balance authority.
